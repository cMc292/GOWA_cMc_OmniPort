# R: the runtime's hot spots, a third pass (2026-11-16)

Decided with the user after U and D ([the S and J review](2026-11-16-s-j-review.md)): R alone. The second pass
([2.15 of the plan](2026-10-29-performance-plan.md)) left the runtime's share of an EDGE job spread over a dozen
mechanisms at 1-2 µs each, under what runs could show. Turns within one run (`GOWA_TURNS`) show about ±0.5%, so a third.

## In short

- **The largest thing was not in the runtime's code:** ~30 million entries a fight run into job modules' and pieces'
  code that no lift had, run by the micro-step at every call. EDGE's job module's static constructor at `0x44D0` (every
  job), the first instructions of every EDGE piece, and entries of three more job modules. The missed-code recorder
  never saw them; now it does, and a new lift took 39 entries: the full path went from 29.96 million entries a run to
  0.59 million.
- **Two runtime changes:** a piece's GET finds its overlay sources by its EA instead of scanning all ~150, and the
  coherency notifier scans the slots' hints four at a time.
- **Measured by turns, all three together:** +2.71% ± 0.50% on four cores. On six cores nothing that one run can show
  (an A/A run there gave -0.24% ± 0.63%).

## How it was looked at

- **Line tables for the runtime** (`PORT_RT_LINES`, new: `gowa.py build -D PORT_RT_LINES=ON`): a PDB, the runtime library
  with `-gline-tables-only`, the code the same.
- **The sampler on the SPU workers** (`PS3_SAMPLE=1`, `PS3_SAMPLE_THREAD=spurs pm`, `PS3_SAMPLE_RVAS`), the fight on six
  cores, EDGE's three lists (w14-16), each sample's address named to its source line by `llvm-symbolizer`. Keep the exe
  and its PDB with the samples: the next build moves the code, and the names come out wrong.
- **What the micro-step runs** (`SPU_SMC_STATS=1`, new): the stubs it runs from memory, and what the full path hands it,
  by address and first words.

The hot lines of EDGE's workers, before (158,264 samples):

| function | of the samples | where |
|---|---|---|
| `spu_overlay_note_get` | 3.76% | the loop over the 16 resident code slots (1.0%), the scan of every source for a piece's EA (0.4-0.9%) |
| `spu_indirect_branch` | 3.23% | the WWS register stubs' memory: holding (0.82%) and running (1.54%) |
| `mfc_do_transfer` | 2.88% | spread |
| `spu_lifted_lookup` | 2.33% | the dispatch cache's compare (1.45%) |
| `spu_coh_notify_write` | 2.03% | the scan of ~99 coherency slots' hints, one at a time (1.18%) |

## The changes

**1. Code no lift had** (`scripts/jobmods_extra.json`, `scripts/spu_pic_pieces.json`, and in the fork the recorder's
call from the full path).

- `SPU_SMC_STATS` showed the micro-step's load: 40 million runs of the WWS register stubs it remembers, all absolute, and
  30 million entries the full path handed it in a fight run of ~40 s. Those were not stubs:

  | where | entries | what |
  |---|---|---|
  | `0x44D0`, EDGE's job module | 5.2 M | a static constructor, called through the module's table at every job |
  | offset 0 of EDGE's pieces (`0x755B80`, `0x75FE80`, `0x758590`, `0x75BD10`, `0x763980`, `0x75F580`, ...) | ~10 M | the instructions before the lifted entry the native hooks sit on (`+0x18` to `+0x90`) |
  | three job modules of other workloads | ~2 M | functions reached through pointers |

- The missed-code recorder ([2026-11-08](2026-11-08-missed-code-profile.md)) watches the interpreter, which these never
  reached: the micro-step ran them and branched back to lifted code. The full path now reports to it, and a fight run
  with `PS3_MISSED_CODE` gave 85 rows; `gowa.py missed --apply` took 39 entries and `gowa.py lift --jobmods-only` lifted
  them. The native hooks are placed by address, so the pieces' new entries at offset 0 still run them.
- After the lift, `SPU_SMC_STATS`: the full path 0.59 million entries a run, all of them WWS stubs the two-entry memory
  missed.

**2. A piece's GET by its EA** (`spu_overlay_note_get`). Each source EA keeps its sources in registration order, and the
signature sources are listed apart; a GET visits those, in the order of the scan they replace. `SPU_OVL_CHECK=1`
compares the two at every GET: 32.8 million GETs, none different. 3.76% to 3.16%.

**3. The coherency notifier's scan** (`spu_coh_next_holder`): four hints a compare (SSE2), the holders checked as
before. 2.03% to 0.82%.

**Tried and taken out:** the WWS stubs by register (`lqd`/`stqd`) decoded too, and a `pshufb` for their quadwords. Here
they are all absolute (none by register in 40 million), and the run came out slower than the compiler's own loop, no
longer inlined. `SPU_SMC_MEMO_CHECK=1` stays: every remembered stub run both ways, decoded and by the micro-step, the
registers, pc, interrupt enable and local store compared; 54.2 million stubs, none different.

**For measuring:** `g_spu_rt_turn` (`spu_context.h`) is the runtime's turn, set by the port's clock with
`GOWA_TURNS=<s>:rt`; `SPU_RT_TURNS=ovl,coh,lift` names which switches follow it; `SPU_LIFT_TURN=<image>:<hex>,...`
leaves a lift's new entries out of the lookup in the turns that are off (their code goes to the micro-step there, as
before the lift), and the dispatch cache keeps the turn in its key while it is set.

## Measured

Turns of 3 s, the fight from 69 to 229 s after the load, one run each:

| what turned | four cores | six cores |
|---|---|---|
| 2 and 3, and the stub change since taken out | +1.32% ± 0.64% | +1.24% ± 0.41% |
| 1, 2 and 3 | **+2.71% ± 0.50%** | -0.60% ± 0.58% |
| 1 alone | | +0.35% ± 0.49% |
| nothing (A/A) | | -0.24% ± 0.63% |

- **Four cores,** where the CPU is full, gain as Gate 0 has it.
- **Six cores** show nothing a run can tell: the A/A run puts one run's reach at about ±1.2%, and the six-core figures
  above fall inside it. Gate 0 found that ~5% of SPU time a six-core CPU takes off shows on the frame.

## What is left

From the sampler after changes 2 and 3 (before the lift): `spu_overlay_note_get`'s slot loop (1%, needs a finer page
map, which changes the context's layout), the dispatch cache's compare (2.5%), `mfc_do_transfer` (2.9%), the stripe lock
(1.7%), `rsx_d3d12_vertex_pass_publish`'s shared sequence counter (1.2%), the drain after each lifted call (2.2%). None
is above 3%, and each needs more than a local change.
